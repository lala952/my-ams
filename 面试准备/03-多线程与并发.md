## 1. 线程池（必考，项目里有现成代码）

### 1.1 为什么用线程池？

项目 `ThreadPoolExecutorUtils` 注释里总结了三点，直接背：
1. **降低资源消耗**：线程复用，避免频繁创建/销毁线程的开销。
2. **提高响应速度**：核心线程常驻，任务来了直接用空闲线程执行。
3. **提高可管理性**：统一管理线程数量、队列、拒绝策略，防止资源耗尽，便于监控调优。

### 1.2 为什么不推荐用 `Executors` 创建线程池？

阿里巴巴手册强制要求，原因是 Executors 底层有 OOM 风险：
- `newFixedThreadPool` / `newSingleThreadExecutor`：用的是**无界队列** `LinkedBlockingQueue`（默认 `Integer.MAX_VALUE`），任务堆积会 OOM。
- `newCachedThreadPool`：`maximumPoolSize = Integer.MAX_VALUE`，会创建海量线程导致 OOM。
- `newScheduledThreadPool`：同样是无界队列。

所以必须用 `new ThreadPoolExecutor(...)` 手动配置——你的 `ThreadPoolConfig` 就是标准示范。

### 1.3 ThreadPoolExecutor 的 7 大参数

```java
new ThreadPoolExecutor(
    corePoolSize,      // 核心线程数
    maximumPoolSize,   // 最大线程数
    keepAliveTime,     // 非核心线程空闲存活时间
    unit,              // 时间单位
    workQueue,         // 任务队列
    threadFactory,     // 线程工厂
    handler            // 拒绝策略
);
```

结合项目 `ThreadPoolConfig`：
| 参数 | 项目取值 | 说明 |
|------|---------|------|
| corePoolSize | `CPU核数`（业务池）/ `CPU核数*2`（IO池） | 业务池 CPU 密集型，IO 池 IO 密集型 |
| maximumPoolSize | core*2 | 预留突发流量 |
| keepAliveTime | 60s | 空闲非核心线程回收 |
| workQueue | `LinkedBlockingQueue(500)` | 有界队列，防 OOM |
| threadFactory | `NamedThreadFactory` | 自定义线程名 `biz-pool-N`，便于排查 |
| handler | `CallerRunsPolicy` | 队列满由调用线程执行，不丢任务 |

### 1.4 线程池执行流程（背熟）

1. 提交任务 → 核心线程满了没？
   - 没满：创建核心线程执行；
   - 满了 → 步骤 2。
2. 队列满了没？
   - 没满：入队等待；
   - 满了 → 步骤 3。
3. 最大线程满了没？
   - 没满：创建非核心线程执行；
   - 满了 → 步骤 4。
4. 执行拒绝策略。

**关键点**：只有**队列满**了才会创建非核心线程，然后才会触发拒绝策略。

### 1.5 4 种拒绝策略

| 策略 | 行为 | 适用 |
|------|------|------|
| `AbortPolicy`（默认） | 丢弃并抛 `RejectedExecutionException` | 必须感知失败的场景 |
| `CallerRunsPolicy` | 调用线程自己执行 | 不允许丢任务（项目用的这个） |
| `DiscardPolicy` | 静默丢弃 | 不重要任务（日志） |
| `DiscardOldestPolicy` | 丢弃队列最旧任务 | 关注最新数据 |

### 1.6 线程池大小怎么设置？

- **CPU 密集型**：`N_CPU + 1`（+1 防止缺页中断导致 CPU 空转）。
- **IO 密集型**：`N_CPU * 2` 或 `N_CPU * (1 + 等待时间/计算时间)`。
- 项目：业务线程池（数据库批量操作）按 CPU 核数，IO 线程池（PDF 导出、附件保存）按 `CPU核数 * 2`。

### 1.7 execute() 和 submit() 的区别

| 对比 | execute(Runnable) | submit(Callable/Runnable) |
|------|-------------------|---------------------------|
| 返回值 | 无 | 返回 `Future`，可 `get()` |
| 异常 | 直接抛出 | 异常被吞，需 `future.get()` 才能拿到 |

项目 `ThreadPoolExecutorUtils.method1/method2` 正好演示了这两者。

## 2. synchronized 底层原理

### 2.1 对象锁升级（无锁 → 偏向锁 → 轻量级锁 → 重量级锁）

synchronized 锁的是对象，锁信息存在**对象头的 Mark Word** 里：

1. **无锁**：无竞争。
2. **偏向锁**：一个线程反复获取，Mark Word 记录线程 ID，无需 CAS。
3. **轻量级锁**：多线程交替执行、无真正竞争，用 CAS 自旋获取。
4. **重量级锁**：真正竞争，线程阻塞，通过**对象监视器（Monitor）**实现，底层依赖操作系统互斥量。

**追问：为什么有锁升级？**
> 为了在无竞争场景下减少加锁开销（偏向/轻量级不需要切内核态），只有真正竞争时才升级到重量级锁。

### 2.2 synchronized 和 ReentrantLock 的区别

| 对比 | synchronized | ReentrantLock |
|------|--------------|---------------|
| 实现 | JVM 关键字，自动释放 | JDK 类，需手动 `lock/unlock` |
| 公平性 | 非公平 | 可公平可非公平 |
| 可中断 | 不可中断 | `lockInterruptibly()` 可中断 |
| 条件 | 一个条件队列 | 多个 `Condition` |
| 锁超时 | 无 | `tryLock(timeout)` |
| 底层 | 锁升级 | AQS + CAS |

**何时用 ReentrantLock**：需要可中断、超时、多条件、公平锁时。

## 3. volatile 与 CAS

### 3.1 volatile 的作用

1. **保证可见性**：写 volatile 变量会立即刷回主内存，读会从主内存读（内存屏障）。
2. **禁止指令重排**：通过内存屏障保证有序性。
3. **不保证原子性**：`i++` 这种读-改-写不是原子的。

**典型应用**：单例模式的**双重检查锁（DCL）**，`instance` 必须 `volatile`，防止指令重排导致拿到未初始化完的对象。

### 3.2 CAS（Compare And Swap）

- 思想：比较内存值是否等于期望值，相等才更新，否则自旋重试。
- Java 里 `AtomicInteger`、`ConcurrentHashMap` 都基于 CAS（底层 `Unsafe.compareAndSwapInt`）。
- **三大问题**：① ABA 问题（用 `AtomicStampedReference` 加版本号解决）；② 自旋时间长 CPU 开销大；③ 只能保证单个变量原子性。
- **结合项目**：`RedisIdWorker` 用 Redis 的 `increment` 而不是 CAS 生成序列号，因为 Redis 命令本身原子；而 JUC 原子类用 CAS。

## 4. AQS（AbstractQueuedSynchronizer）

- AQS 是 JUC 的基石，`ReentrantLock`、`Semaphore`、`CountDownLatch` 都基于它。
- **核心思想**：用 `volatile int state` 表示同步状态 + **CLH 双向队列**存放等待线程。
- **独占模式**（ReentrantLock）与**共享模式**（Semaphore、CountDownLatch）。
- `ReentrantLock` 可重入通过 state 自增实现。

**结合项目**：`ThreadPoolExecutorUtils.method4` 用了 `CountDownLatch`（共享模式）等待多个异步任务完成，这就是 AQS 共享模式的典型应用。

## 5. ThreadLocal

### 5.1 原理
- 每个线程持有一个 `ThreadLocalMap`，key 是 `ThreadLocal` 对象（弱引用），value 是值。
- 每个线程只能读写自己的值，天然隔离。

### 5.2 内存泄漏问题（必考）
- `ThreadLocalMap` 的 key 是**弱引用**，`ThreadLocal` 对象被 GC 后 key 变 null，但 value 是强引用，无法访问也无法回收，造成**内存泄漏**。
- 解决：用完调用 `remove()`。

### 5.3 结合项目 —— TransmittableThreadLocal（重要加分点）
项目依赖里有 `transmittable-thread-local`。你要能讲：
> 普通 `ThreadLocal` 在**线程池场景**下失效——因为线程被复用，且父线程的 ThreadLocal 值无法传递给子线程/线程池线程。
> 若依框架用 `TransmittableThreadLocal` 解决**线程池复用导致上下文丢失**的问题（如登录用户信息、TraceId 在异步任务里丢失）。
> 我项目里用 `CompletableFuture` + 线程池做并行查询时，需要保证用户上下文能传递，所以引入了 `transmittable-thread-local`。

## 6. CompletableFuture 异步编排（项目重点）

### 6.1 为什么用？
- JDK8 提供的异步编排工具，支持任务**串行、并行、组合**，比 `Future` + `CountDownLatch` 更优雅。
- 项目 `ChangeServiceImpl` 用 `CompletableFuture` **并行查询四个审批状态的数量**，显著提升统计接口响应速度。

### 6.2 常用 API

```java
// 异步执行
CompletableFuture.supplyAsync(() -> 查DB1, executor)
// 串行：上一步结果做下一步
.thenApply(result -> ...)         // 有入参有返回值
.thenAccept(result -> ...)        // 有入参无返回
.thenRun(() -> ...)               // 无入参无返回
// 组合多个
CompletableFuture.allOf(f1, f2, f3)   // 全部完成
CompletableFuture.anyOf(f1, f2)       // 任一完成
// 异常处理
.exceptionally(e -> 降级值)
// 获取结果
future.get() / join()
```

### 6.3 结合项目的讲法
> 在资产变动列表的统计接口里，原本串行查 4 个状态（草稿/审批中/已完成/已驳回）需要 4 次 DB 往返，我改成用 `BIZ_EXECUTOR` 线程池 + `CompletableFuture.supplyAsync` 把 4 个查询**并行**提交，最后 `allOf` 等待结果，接口耗时从串行的 4 倍降为接近单次查询的耗时。

## 7. 死锁

- **四个必要条件**：互斥、持有并等待、不可剥夺、循环等待。
- **预防**：破坏任一条件即可，常见做法是**按固定顺序加锁**、超时放弃。
- **排查**：`jstack PID` 查看线程状态，能看到 `Found one Java-level deadlock`。

## 附：高频面试题速答

1. **线程有几种状态？** — NEW / RUNNABLE / BLOCKED / WAITING / TIMED_WAITING / TERMINATED。
2. **wait() 和 sleep() 区别？** — wait 释放锁、只能在同步块里、由 notify 唤醒；sleep 不释放锁、到时间自动醒、随处可调。
3. **start() 和 run() 区别？** — start 启动新线程并调用 run；直接调 run 只是普通方法调用。
4. **线程池 shutdown 和 shutdownNow？** — shutdown 平滑关闭（执行完队列任务）；shutdownNow 立即中断、返回未执行任务列表。
5. **什么是线程安全？** — 多线程并发访问共享数据时结果正确，无脏数据/覆盖。
6. **乐观锁和悲观锁？** — 乐观锁用 CAS/版本号，冲突少效率高；悲观锁用 synchronized/数据库行锁，冲突多。
7. **CountDownLatch 和 CyclicBarrier 区别？** — CountDownLatch 一次性、计数递减；CyclicBarrier 可复用、计数递增、到达屏障一起放行。
8. **可重入锁是什么？** — 同一线程可重复获取同一把锁，state 计数，ReentrantLock/synchronized 都是。
9. **volatile 能保证原子性吗？** — 不能，只能保证可见性和有序性。
10. **为什么 HashMap 线程不安全而 ConcurrentHashMap 安全？** — 见 01 篇。
